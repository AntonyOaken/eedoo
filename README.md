# Попути

Пешеходные прогулки: Санкт-Петербург, Курган, Пхукет. React 19 / TypeScript / Next.js 16 / Leaflet; PostgreSQL + PostGIS; Redis; S3-совместимое хранение фото; Nginx и Docker Compose. Импорт исходных наблюдений 2ГИС выполняет Python. Фото вынесены из текущего дерева Git и сохраняются отдельно; старые версии остаются в истории. История Sites сохранена в Git, миграция — ветка `migration/self-hosted`.

## Разработка

Node.js 24, pnpm 11.25.0, Python 3.12+ с Pillow. `pnpm install --frozen-lockfile`, затем `pnpm dev`. Для разработки без PostgreSQL: `pnpm catalog:export`, затем `CATALOG_BACKEND=seed pnpm dev`; этот режим запрещён в production без специального разрешения. Каталог не входит в клиентский JavaScript. Граф улиц выбранного города загружается по требованию в Web Worker; основной и альтернативные локальные маршруты вычисляются там.

## Перенос на VPS

1. Скопировать `.env.example` в `.env`, заменить пароли, согласовать `DATABASE_URL` с `POSTGRES_PASSWORD`, настроить `APP_ORIGIN`, собственный/договорной `TILE_URL`, S3 и публичный URL бакета. S3 ключи доступны только серверу; публичный доступ нужен объектам, а не всему управлению бакетом. `VALHALLA_URL` и `PHOTON_URL` задают заменяемые сервисы. Без Valhalla используется локальный worker, без Photon поиск ограничен собственным каталогом.
2. `docker compose up -d db redis`; `docker compose --profile tools run --rm tools pnpm db:migrate`.
3. `docker compose --profile tools run --rm tools pnpm catalog:export`; `docker compose --profile tools run --rm tools pnpm catalog:import work/catalog.json`.
4. Восстановить `public/photos` из архива данных; `docker compose --profile tools run --rm tools pnpm media:upload`.
5. `docker compose up -d --build app nginx`. По умолчанию только `127.0.0.1:8080`: доступ проверяют SSH-туннелем, без публичного открытия. Когда появятся VPS и домен, добавить HTTPS перед Nginx и установить внешний `APP_ORIGIN`; до этого геолокация на внешнем HTTP недоступна.

В сборке контейнера нет `public/photos`; карточки получают ссылки из таблицы `media_objects`. Каталог в PostgreSQL обновляется независимо от приложения. Исходные JSON сохранены для первого экспорта и восстановления; изменение импортёра для записи произвольных новых источников не означает, что продолжается браузерный сбор данных. `work` содержит снимки и журнал и монтируется отдельно.

## Импорт и откат

`pnpm catalog:export [path]` формирует проверенный снимок всех городов/режимов. `pnpm catalog:import path` проверяет его, загружает новую ревизию в транзакции и атомарно переключает каталог. При ошибке прежний каталог остаётся активным. SHA-256 обеспечивает идемпотентность. `pnpm catalog:rollback <revision>` переключает на прежнюю сохранённую ревизию.

`python scripts/managed-import.py --discoveries PATH --observations PATH --baseline PATH [--publish]` обрабатывает сохранённые наблюдения Петербурга, запрещает параллельные запуски, ведёт `work/import-journal.jsonl`, запускает проверки и публикует только валидированный снимок при `--publish`. Это управляемый разовый процесс; он не запускает автоматический парсинг 2ГИС. У существующих исходных импортёров и очередей сохраняется история и checkpoint. Работа с правовыми вопросами отложена.

## Проверки и эксплуатация

`pnpm typecheck`, `pnpm test`, Python import tests, `pnpm build`. `pnpm test:integration` требует отдельную тестовую PostgreSQL/PostGIS и проверяет транзакции/пространственные запросы. CI использует `poputi_test`.

`/api/health/live` — процесс; `/api/health/ready` — база/ревизия/Redis. Метрики Prometheus `/api/metrics` защищены `METRICS_TOKEN` и скрыты Nginx; опрос внутри backend-сети. Ответы API содержат request ID, журналы ошибок — структурированные JSON без адресов/персональных данных. Ограничения Redis общие для инстансов; при недоступном Redis API отвечает 503. Nginx перезаписывает X-Forwarded-For, поэтому доверять заголовку можно только за ним.

`ops/backup.sh` создаёт pg_dump с контрольной суммой; `ops/restore.sh FILE` проверяет восстановление в отдельной `poputi_restore`, не меняя рабочую базу. Переносить копии во внешнее хранилище и включить версионирование S3 на выбранном провайдере; регулярную задачу настроить на VPS после первого успешного восстановления. Пока VPS нет, расписание не установлено.

Ступени нагрузки: `LOAD_USERS=100|300|1000 LOAD_SECONDS=30 pnpm test:load http://staging:8080`. Сценарий измеряет просмотры каталога, показывает p95/p99, ошибки и 429; он не доказывает поддержку 1000 пользователей со всеми сценариями. Для приёмки отдельно добавить расчёт маршрутов, S3/тайлы, свежий импорт, мобильные устройства, отказ Redis и восстановление базы. Production-сервисы и пользовательские сеансы нагрузочным тестом не проверяют.

Оригинальная опубликованная версия Sites 55 не изменена. Публикация на VPS и оценка реальной мощности невозможны до выбора сервера/провайдеров. Ветка миграции заменяет инфраструктуру Sites и предназначена для собственного сервера.
